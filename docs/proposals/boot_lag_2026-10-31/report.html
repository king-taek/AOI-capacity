시작 화면 렉 개선안

결과 HTML 을 열 때 나오는 4초 랜딩 애니메이션(D104 '데이터 입자')이 끊기는 원인과 고친 안 9개 + 결정된 T2 의 세 버전. 2026-10-31~11-01 계측, 30일치 19MB 파일 기준.

결론 — 지금 장면은 프레임마다 입자 16,000개를 선으로 긋느라 끊긴다. 그리는 방식만 바꾼 V2 픽셀 버퍼가 같은 장면을 3배 매끄럽게(프레임 간격 p95 기준) 만들고, 디자인을 바꿀 수 있다면 스캔 라인 · CSS · 글자 안은 프레임마다 JS 가 0 이라 어떤 PC 에서도 끊길 거리가 없다. 어느 안이든 걷힐 때의 전체 화면 blur 는 뺀다.

왜 끊기나 — 현재 코드 진단
  • 프레임마다 너무 많이 한다. 입자 16,000개 × curl noise 4번 + Path2D 꼬리 선 16,000개 · 네모 16,000개를 팔레트 40색마다 stroke/fill. 콜백만 p50 3.1ms, 그 뒤 래스터(선 16,000개를 alpha 로 긋기)가 따로 든다.
  • dpr 2 까지 그린다. 125~150% 배율이면 픽셀이 1.6~2.3배. dpr 1.5 에서 12fps.
  • Worker 라도 CPU 는 나눠 쓴다. 메인이 19MB JSON 을 해석하는 동안 코어 하나를 다 쓰고 래스터 · 합성기 · Worker 가 나머지를 나눈다. 4코어에서 현재 코드는 그 구간에 실행마다 16~45fps 로 흔들렸다.
  • 걷힐 때 전체 화면 blur(5px) + scale. 메인이 첫 화면을 그리는 순간과 겹친다. blur 만 빼면 걷힘 구간 p95 108 → 48ms.
  • OffscreenCanvas 가 없는 브라우저(옛 Edge)는 전부 메인 스레드 — JSON 해석 동안 0프레임.

기준: animation-performance(합성 전용 속성 · 메인 스레드 밖 · 프레임 예산) · improve-animations 성능 항목 · design-motion-principles 생성 체크(blur 상한 · 반복 맥동 금지 · reduced-motion).

어떻게 쟀나 · 주의
  • 30일치 보관 샘플(Report 55,717개)을 현재 template 에 넣은 19.3MB 결과 HTML 에서 boot 스크립트만 교체. Playwright Chromium 153(헤드리스 · 소프트웨어 합성 · 4 vCPU). 조건: 기본(1920×1080 · dpr 1) · CPU 4배 느리게(메인 스레드만) · dpr 1.5.
  • 지표: Worker rAF 간격(실제 화면 갱신)과 콜백 시간 · 합성기 드롭(CDP 트레이스) · 걷힘 구간 메인 rAF 간격 · long-animation-frame.
  • 절대값은 현장 PC(Windows · 내장 GPU) 와 다르다 — 안 사이의 상대 비교로 읽는다. 고른 안은 현장 노트북(125~150% 배율 · 실데이터 · Edge/Chrome)에서 확인한다.
  • 모든 안이 지키는 것: 4초 최소 · 바깥 요청 0 · AOI_BOOT 인터페이스 그대로(template 나머지 무변경) · reduced-motion · 걷힘은 opacity 만.

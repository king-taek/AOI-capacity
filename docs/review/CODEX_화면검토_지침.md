# AOI 가동 현황 HTML — 화면 개선 검토 지침 (Codex 용)

> 이 문서를 처음부터 끝까지 읽은 뒤 작업을 시작하세요. 첨부된 HTML 한 장(`AOI_capacity*.html`)이 검토 대상입니다.
> 작업은 **4단계**이고, 단계마다 멈추는 지점이 있습니다. **2단계(질문)에서 반드시 사용자의 답을 기다리세요.**

---

## 0. 이 화면은 무엇인가

- 반도체 공장의 **AOI(자동 광학 검사) 장비 38대**(Camtek 30대 + KLA 8대)가 하루 24시간 중 얼마나 실제로 검사했는지(가동률)를 보여 주는 **정적 HTML 대시보드 한 장**입니다.
- PyQt6 수집 프로그램이 NAS 의 BatchReport · WaferInfo.ini 를 읽어 이 HTML 을 만들고, 사용자는 **더블클릭해서 브라우저(Chrome/Edge)로 엽니다.** 서버 없음.
- 사용자: 현장 엔지니어·관리자(한국어). 하루에 몇 번 열어 "어느 장비가 놀았나 · 어디서 Error 가 났나 · 레시피(검사 조건)별로 Wafer 한 장 스캔에 몇 분 걸리나" 를 봅니다.
- 화면 글자는 **한국어**, 장비명 · Job · Lot · Wafer ID · 상태 원문은 **영어 원문 그대로**입니다(번역하면 안 됨).

## 1. 반드시 지켜야 할 제약 (제안도 이 안에서)

1. **바깥 요청 0건.** CDN · 웹폰트 · 이미지 URL · fetch 금지. 라이브러리는 파일 안에 인라인(GSAP 3 + Flip, animate.css 일부, lottie_light 가 이미 들어 있음). 새 라이브러리 제안은 "인라인 가능한 크기인지" 함께 적으세요.
2. **데이터 · 계산 규칙은 이번 검토 범위가 아닙니다.** 가동률 공식, Error 판정, Scan/Rescan 구분, INI 시각 규칙, 멀티/단일 판정 같은 것은 사용자가 확정한 규칙입니다. 숫자가 이상해 보이면 "질문" 으로만 올리고 바꾸자고 하지 마세요. 대상은 **보여 주는 방식 · 구조 · 문구 · 상호작용 · 움직임**입니다.
3. **틀은 그대로, 내용만 바뀐다.** 사용자가 여러 번 지적한 것: 버튼을 누를 때 화면 전체가 다시 그려지거나 흔들리는 느낌을 싫어합니다. 렌더는 키 있는 morph(`data-key`)로 바뀐 노드만 고치고, 등장 연출은 **뷰나 팝업이 처음 들어올 때 한 번**뿐입니다. 클릭마다 반복되는 큰 움직임은 제안하지 마세요.
4. **라이트 테마 단일**, 색은 상수에서만: Scan(진한 파랑) · Rescan(연한 파랑) · Test(보라) · Error(빨강) · 에러 후 대기(연한 빨강) · 대기(회색). 멀티 = 짙은 회색, 단일 = 파랑.
5. **화면 용어 고정**: Scan · Rescan · Test · Error · 에러 후 대기 · 대기 · 가동률 · Lot · Wafer · Job · Report. 옛 용어(가동 · 중복스캔 · 재스캔 · 미가동 · 정지 · 중단)는 다시 쓰지 않습니다.
6. 좁은 화면(≤ 820px)에서도 쪽 가로 스크롤이 없어야 합니다(탭 줄만 옆으로 밀림). `prefers-reduced-motion` 이면 이동 없이 opacity 만.
7. 접근성: 팝업이 열리면 아래는 inert, Tab 은 맨 위 팝업 안에서만, ESC 는 맨 위 팝업만 닫음, 포커스 복원.
8. 브라우저 자동 번역은 꺼 두었습니다(`translate="no"`). 번역된 화면을 기준으로 문구를 평가하지 마세요.

## 2. 화면 지도 — 빠짐없이 열어 볼 것

HTML 을 브라우저(가능하면 Playwright/Chromium, 1440×900 과 390×844 두 크기)로 열고 아래를 **전부** 눌러 보세요. 함수 이름은 HTML 안 `<script>` 에서 찾을 수 있습니다(handoff 에서 위치를 가리킬 때 쓰세요).

### 머리(공통) — `headerHtml` · `rangeHtml`
- 브랜드(웨이퍼 스캔 Lottie) · 상단 탭 4개: **가동률 · Error · TB500 · Kendall · 레시피** (탭 아래 파란 표시자가 물리 모델로 늘었다 줄며 이동)
- 기간: 프리셋 **최근 7일 · 1달 · 전체** + 날짜 두 칸 + 'n일'
- 날짜 이동 ‹ › · '최신' · '사본 저장' · '레시피 묶음' 팝업 · 기간 칩 · 수집 시각 · (있으면) 수집 상태 칩
- 바닥글 `footHtml`: 수집 범위 · 계산 규칙 한 줄 설명

### 탭 1 — 가동률 `homeHtml`
- 카드 3장(평균 가동률 · 살펴볼 장비 · Error 등), **층(전체·2층·4층) · 장비 종류(전체·Camtek·KLA) 필터 두 줄**, 정렬
- 장비마다 **24시간 막대**(Scan/Rescan/Test/Error/에러 후 대기/대기 색 구간) — 처음 그릴 때 왼쪽→오른쪽으로 쓸리듯 나타남
- 행 클릭 → **장비 팝업** `devPopupHtml`: 통계 6 · 하루 막대 · Lot 이름표(지시선) · Lot 선택 시 원문 상자 · 'Report 열기'
- 장비 팝업에서 Error → **Error 상세 팝업** `errPopupHtml`: 언제 났나(타임라인) · 유형별 · 최근 21일 막대(누르면 그 날만, 끌면 창 이동) · Lot 별

### 탭 2 — Error `errorsHtml` (KLA 제외)
- 기간 · 층 · 지표(건수/시간) → 날짜별 막대 → **유형별 · 장비별 · Job별** 세 목록(줄은 제자리, 글자만 한 글자씩 넘어가는 연출)
- 각 행의 깔때기 버튼(유형/Job/장비 필터, 함께 걸림) · 필터 칩
- 유형/Job 행 → **유형·Job 팝업** `typePopupHtml` → 장비별 → Error 상세 팝업

### 탭 3 — TB500 · Kendall `reportHtml`
- 표기명 21개 Job 만. Kendall · TB500 두 묶음 표, 열 머리 눌러 정렬, 행 펼침(높이 0 에서 열림)

### 탭 4 — 레시피 `rcpHtml` · `cmpHtml` (가장 최근에 크게 바뀐 화면 — 중점 검토)
- 왼쪽: 검색 · 범례 · **레시피 한 줄 = 멀티/단일 Job 을 합친 것**(Wafer 수 · 멀티/단일 비율 막대 · '멀티 n%')
- 오른쪽 위: 레시피 이름 · '이 레시피로 보는 Job' 칩 · **멀티 / 단일 / 차이 타일**(장당 분 · 시간당 · 'n장 중 m장으로 계산' · 'INI a장 + Report 로 채운 b장 · INI 만 x분' · 배치 기준) · 10~90% 띠
- **장비별 장당 스캔**: 같은 장비의 멀티●–단일● 점 그래프 · 차이 · 장 수
- **어떻게 셌나**: 장 · INI · 배치 · Lot · 판정 · 계산 여섯 칸(실제 숫자와 뺀 이유)
- '상세 보기'(Job 하나씩 고름 → 카드 5 · 장비별 상세 표 · 날짜별 막대) · '전후 비교 열기'(두 기간 × 두 레시피 묶음, ＋/✕ 칩)

### 팝업 덱 — `popupsHtml` · `stackbarHtml`
- 팝업 위에 팝업을 열면 아래 것은 왼쪽 뒤로 물러남(3D 회전·어둡게), 뒤 카드가 보이는 곳을 누르면 앞으로, 왼쪽 위 **스택 바** 칩으로 전환, ESC 는 맨 위만
- '레시피 묶음' 팝업 `recipePopupHtml`: Job 원문을 묶어 이름 붙이기(브라우저 localStorage 에 저장 · 내보내기)

### 꼭 확인할 움직임 목록
탭 전환(가로 미끄러짐 + 표시자) · 카드 숫자 카운트업 · 24시간 막대 sweep · 막대 그래프 등장(scaleY) · 목록 글자 넘김 · 팝업 등장/퇴장/덱 이동/앞으로 오기 · 리포트 행 펼침 · Lot 이름표 차례로 내려옴 · 로딩 Lottie · reduced-motion 일 때.

## 3. 무엇을 보고 평가할 것인가

아래 관점으로 **각 화면마다** 문제를 찾으세요. 근거(어느 화면 · 어느 요소 · 무엇이 왜 불편한가)를 꼭 붙입니다.

- **한눈에 보이는가**: 그 화면에서 가장 중요한 숫자/결론이 3초 안에 보이는가, 시선 순서, 정보 밀도(너무 많음/부족함), "상세로 미뤄야 할 것"
- **구조**: 탭 · 팝업 · 접힘의 나눔이 자연스러운가, 같은 정보가 여러 곳에 흩어졌거나 중복되는가, 돌아오는 길(뒤로 · ESC · 칩)이 분명한가
- **텍스트**: 어색한 한국어 · 번역투 · 너무 긴 설명 · 같은 개념에 다른 단어 · 단위 표기(분/장, %, 장, 개) · 숫자 서식
- **데이터 시각화**: 차트 형태가 질문에 맞는가, 축·눈금·범례, 색만으로 구분하지 않는가, 레이블 겹침, 빈 값('—')의 의미
- **버튼 · 상호작용**: 무엇이 눌리는지 보이는가(어포던스), 상태 표시(켜짐/꺼짐), 클릭 영역 크기, 키보드
- **애니메이션**: 의미를 돕는가 방해하는가, 길이(상태 150~300ms · 레이아웃 300~500ms 기준), 반복되어 거슬리는 것, 끊김
- **좁은 화면(390px)**: 잘림 · 겹침 · 줄바꿈 · 터치 영역
- **성능 체감**: 큰 기간(전체)에서 열기 · 탭 전환이 버벅이는가(측정했다면 숫자로)

## 4. 진행 방법 (4단계)

### 1단계 — 읽고 둘러보기
이 지침을 읽고 HTML 의 모든 화면 · 버튼 · 움직임을 직접 확인합니다. 스크린샷을 찍을 수 있으면 찍어 두세요. 아직 개선안을 쓰지 마세요.

### 2단계 — 사용자에게 질문하고 **멈추기**
둘러본 결과를 짧게(문제 후보 목록, 각 한 줄) 보여 준 뒤, 개선 방향을 정하는 데 필요한 질문을 **최대 10개**, 번호를 붙여 묻습니다. 예:
- 누가 · 언제 · 어떤 화면으로 주로 보는지(모니터 크기, 회의 화면 공유 여부)
- 가장 자주 하는 질문 세 가지
- 애니메이션을 얼마나 원하는지(지금보다 줄이기/유지/늘리기)
- 레시피 탭에서 멀티 vs 단일 다음으로 중요한 것
- 각 문제 후보의 우선순위
**여기서 멈추고 답을 기다리세요.** 답 없이 3단계로 넘어가지 마세요.

### 3단계 — 개선안마다 예시 3개
답을 반영해 개선안을 정리하고, **개선안 하나마다 서로 다른 방향의 예시 3개(A · B · C)**를 만듭니다.
- 예시는 **실제로 볼 수 있는 형태**로: 그 부분만 떼어 낸 작은 HTML/CSS(외부 요청 없이, 이 파일의 색·글꼴 토큰을 그대로 써서) 또는 스크린샷 위 주석. 말로만 쓰지 마세요.
- 예시마다 장점 · 단점 · 구현 크기(작음/중간/큼) · 위 제약 1~8 중 걸리는 것이 있는지.
- 세 예시는 "조금 다듬기 / 구조 바꾸기 / 과감한 안" 처럼 폭이 달라야 합니다.
- 다 보여 준 뒤 사용자에게 개선안마다 A/B/C(또는 섞기 · 빼기)를 고르게 하고 **다시 멈춥니다.**

### 4단계 — 최종 handoff 작성
사용자가 고른 것만으로 아래 형식의 **handoff 문서 한 장**(Markdown)을 씁니다. 이 문서는 Claude Code 가 그대로 받아 구현합니다 — 구현자가 추측하지 않도록 구체적으로.

```markdown
# AOI 화면 개선 handoff — <날짜>

## 요약
- 고른 개선안 n개, 우선순위 순. 한 줄씩.

## 사용자 답변 (2단계 · 3단계에서 받은 것 그대로)
- Q1 … → A …

## 개선안 1 — <제목>   (우선순위 P1/P2/P3 · 크기 S/M/L)
- 화면/위치: <탭 · 팝업 · 영역>, 관련 함수/선택자: `rcpHtml` · `.dbrow` …
- 지금: <무엇이 어떻게 보이는지 · 왜 문제인지(근거)>
- 바꿀 것: <고른 예시(A/B/C) 기준의 정확한 모습 — 배치 · 문구(한국어 원문 그대로) · 색(상수 이름) · 크기 · 상태별 모습 · 빈 값일 때 · 390px 일 때>
- 움직임: <있으면 대상 · 시점(처음 한 번/값이 바뀔 때) · 길이 · easing · reduced-motion 일 때>
- 예시 코드: <3단계에서 고른 HTML/CSS 조각>
- 받아들임 기준: <브라우저에서 무엇을 누르면 무엇이 보여야 하는지 — 테스트로 옮길 수 있게 3~6줄>
- 건드리지 말 것: <같이 바뀌면 안 되는 것>

## 개선안 2 — …

## 고르지 않은 것 · 나중에
- …

## 데이터 · 규칙 질문 (구현 범위 밖, 사용자 확인 필요)
- …
```
